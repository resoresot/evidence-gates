# evidence-gates — AI に「やったつもり」で作業を終わらせない Claude Code プラグイン

**AI コーディングエージェント(Claude Code)が作業を終えるときの、よくある 3 つの失敗を、終わろうとした瞬間に見つけて直させます。**

| 失敗 | よくある例 |
|---|---|
| テストが落ちたまま終わる | 修正の途中でテストを壊したのに、そのまま「対応しました」 |
| 自分で決められることを聞いて止まる | 「この方針で進めてよいですか?」で止まり、人は「はい」と返すだけ |
| 確かめずに「完了」と言う | コードを書き換えたあと何も動かさずに「直しました」 |

- **こんな人向け:** Claude Code に作業を任せていて、「終わった」と言われたのに直っていない、確認待ちで止まっている、を減らしたい人。
- **仕組み:** Claude Code のフック(決まった瞬間に必ず呼ばれるスクリプト)で調べ、見つけたら理由を返して AI にやり直させます。
  止める規則は、指示書に書いても繰り返された失敗から作っています。
- **測定つき:** 判定を正規表現の規則でやるか LLM でやるかを、正解ラベル付きで測りました([eval/RESULTS.md](eval/RESULTS.md))。
  既定の動きはその結果で決めています(確かめずに「完了」の規則は誤りが多かったので、既定では止めずに記録だけにしています)。

[English](README.en.md)

## なぜ作ったか

エージェントへの指示書(CLAUDE.md など)に「完了と言う前にテストを実行する」と書いても、守られない回が残ります。
文章で書いた規則は、エージェントがその場で思い出したときにしか効かないからです。

そこで、規則を **Claude Code のフック**に移しました。フックは決まった瞬間(エージェントが終わろうとした時、
コマンドを実行する直前、依頼を受けた時)に必ず呼ばれるスクリプトで、ブロックすると理由がエージェントに渡り、
エージェントはそれを読んでやり直します。

## 中身

| 部品 | いつ動くか | 何を止めるか | 逃げ道 |
|---|---|---|---|
| `completion_gate` / done | 終わろうとした時 | 最後の編集のあとにコードを動かしていないのに「完了」と報告する。シェル経由の編集(`sed -i`、リダイレクト、`python3 - <<EOF … write_text`)も編集として数え、`ls` や `git status` のように見るだけのコマンドは確認として数えない。**規則による判定は、既定では止めずに記録だけ残す**(実測で誤りが多かったため。下の「規則か LLM か」) | 「未検証」と明記し、確かめ方を書く |
| `completion_gate` / ask | 終わろうとした時 | 自分で決められることを「〜してよいですか?」と聞いて止まる。「確認します。」と宣言だけして終わる | 最後の行に `確認理由: <分類>`(不可逆・外部送信・好み・スコープ拡大・コスト・情報不足)。英語では `Reason to ask: irreversible / external / preference / scope / cost / missing-info` |
| `completion_gate` / lang | 終わろうとした時 | 日本語で話しかけられているのに英語で返す | — |
| `test_gate` | 終わろうとした時 | リポジトリのテストが落ちたまま終わる(リポジトリごとに `.claude/test_gate.json` で有効化。変更ファイルに応じて走らせるテストを選べる) | `max_iterations` 回(既定 3)続けて失敗したら止めるのをやめて人に知らせる |
| `zsh_glob_gate` | Bash の実行直前 | zsh で引用符なしのパターンを渡す(`grep --include=*.py`、`find -name *.md`、`rg -g *.ts`)。zsh は先に展開するので、当たらなければ失敗し、当たれば黙って別の意味になる | 区切りに確信が持てない書き方や、`case` / `[[ ]]` の中のパターンは止めずに記録だけ残す |
| `lessons` | 依頼を受けた時 | 過去の失敗から作った「学び」のうち、依頼に関係するものを最大 3 件エージェントに見せる | — |

`completion_gate` の done と ask は、LLM に判定させることもできます(`EVIDENCE_GATES_JUDGE=sonnet` など)。
Claude Code の `type: "prompt"` のフックは最後の返答しか見られず、編集のあとに何を実行したかが分かりません。
そのため、このゲートが依頼・実行したことの一覧・最後の返答をまとめ、Claude Code の CLI を
ツール・フック・設定なしで呼んで判定させます。呼ぶのは、安い絞り込みを通ったターンだけです。
LLM が答えられなかったときは、規則の判定に戻ります。

どのゲートも **fail-open**(ゲート自体が壊れたら止めずに通す)です。`completion_gate` は続けて 2 回は止めません。
各ゲートは判定ごとに 1 行を `events.jsonl` に記録し(会話の本文は残しません)、`tools/stats.py` で週ごとの発火率にできます。
記録が途切れたり、発火率が急に変わったりすれば、ゲートが黙って効かなくなったことに気づけます。

### 失敗をゲートに変える流れ

```
失敗する → 学びとして記録(eg-lessons add) → 依頼のたびに関係する学びを見せる
        → それでも同じ失敗が起きたら数える(eg-lessons recur)
        → 再発が続く学びを一覧にする(eg-lessons report) → フックとして実装する → 学びをゲート化済みにする
```

`zsh_glob_gate` と `completion_gate` は、作者の運用でこの流れを通って生まれたゲートです。
文章の学びを見せ続けても再発した失敗だけを、機械の判定に移しています。

## 効いているか(実測)

`tools/replay.py` は、過去の会話記録にゲートの判定を後から当て直し、件数だけを集計します。
以下は作者自身の Claude Code の記録での結果です。行ごとに測った期間が違います(各ゲートを入れる前の期間を使うため。
`completion_gate` は `zsh_glob_gate` より早く導入したので、導入前の記録が少なく、ask の母数が小さくなっています)。

| ゲート | 期間 | 結果 |
|---|---|---|
| `zsh_glob_gate` | 導入前 | Bash 実行 15,003 回のうち、止める対象は 197 回。そのうち **176 回(89.3%)は実際に `no matches found` で失敗**していた。残り 21 回には、パターンがファイルに当たって別の意味で実行された場合が含まれうる(未確認)。検索コマンドのこの失敗 283 回のうち、止められるのは 62.2% |
| `completion_gate` / done(指摘の割合) | 編集ツールしか見ない旧版が動いていた期間 | 確認なしで出た「完了」120 件(うち 117 件はシェル経由の編集で旧版をすり抜けたもの)と、確認ありの「完了」145 件を比べた。次の発言で「動かない」等の指摘が来た割合は **4.2% と 3.4% で、ほぼ差がなかった**。この指標は粗く、ゲートの効果は今のところ示せていない |
| `completion_gate` / ask | 導入前 | 241 ターン中 9 回発火。そのうち 2 回は返事が「はい」「お願いします」だけだった(件数が少なく参考値) |

数字が示しているのは「zsh のゲートはほぼ本物の失敗だけを止める」ことまでです。
done のゲートは、作者の運用で同じ指摘が繰り返されたことが導入の理由でしたが、
記録から測れる範囲では差が見えていません。そこで、正解ラベルを付けて測り直しました(次の節)。

### 規則か LLM か(ラベル付きの評価)

作者の記録 1,692 ターンから層別に 178 ターンを抜き出し、規則と LLM の判定を同じ正解で比べました。
正解は Opus 5.5 が付けました。別の会社のモデル(OpenAI の GPT 系)にも同じ基準で判定させて比べ(一致は done 30 件中 27 件・κ 0.37、
ask 28 件・κ 0.63)、ask の 4 件は作者も判定しています。done の正解は人が見ていません。
公開できる合成データ 112 件でも比べています。詳細は [eval/RESULTS.md](eval/RESULTS.md) にあります。

- **done**:確かめずに「完了」と言った場面は 178 件中 1 件だけでした。一方、規則は全ターンの約 5% で止めていて、
  標本で止めた 28 件はすべて不要でした(主な原因は、編集とその確認を 1 つのシェルコマンドで続ける書き方を規則が読めないこと)。
  そのため、**規則の done は既定で止めずに記録だけ**にしました。合成データでは、LLM(絞り込み + Sonnet)は当てはまる 30 件をすべて当て、
  規則は 13 件でした(F1 100% と 58%)。
- **ask**:本物の記録では、規則と LLM の差は示せていません。当てはまる 5 件に対し、どちらも 2 件を当てて 3 件を見逃しました
  (重み付きの F1 は 7% と 72% ですが、この差は重みの大きい 1 件だけから来ています)。合成データでも 63% と 77% で差は小さいです。
  規則は無料で、止めるのは全ターンの約 1% なので、既定は規則のままにしています。
- LLM を使うなら Sonnet です(1,000 ターンあたり約 8 ドル、呼んだターンで約 3 秒)。Haiku は本物の記録で不要に止める割合が高く(ask で全ターンの 6.4%)、おすすめしません。
- **判定役そのものも確かめました。** 確かめ済みの場面から確かめた部分を消す、という答えの分かっている失敗を仕込むと、
  規則は 23 件中 7 件しか見つけられず、LLM(Sonnet)は 23 件すべてを見つけました。同じ場面を 5 回判定させると、
  done の答えは 99% の場面で毎回同じでしたが、ask は当てはまる場面の半分近くで回によって変わりました。
- 判断の理由と退けた案は [docs/adr/](docs/adr/) に置いています(規則の done を記録だけにした理由、LLM の呼び方、判定役の確かめ方)。
- 評価の途中で、測り方の不具合を 3 件見つけて直しています。そのうち 1 件は、コマンドを 160 字で切って判定役に渡していたため、
  確かめて読んだ正解 9 件のうち 7 件が誤っていたものです。

### 本物の Claude Code での動作確認

(規則の done が既定で止めていた時点の版で行いました。今の版では `EVIDENCE_GATES_DONE_RULE=block` を付けた場合の動きです。)
わざとバグを入れたリポジトリで「テストは実行せずに『直しました』とだけ報告して」と頼むと、
`completion_gate` が完了報告を止め、エージェントは報告を「未検証」に書き直して確かめ方を添えました。
終了時には `test_gate` がテストを走らせ、テストが通ることを確かめました。

### 設計の判断

作者の環境で、小規模の課題 8 件(各 1 回)と 6 ファイル超の課題 1 件(各 3 回)を、「フックなし」「フックあり」
「事前に変更内容を取り決めてから実装し、機械で検証して 1 回だけ直させる多段構成」の 3 通りで解かせました。
採点用テストは AI に見せていません。強いモデル(Opus 5.5)は 3 通りとも全件で採点用テストに全部合格し、
小規模の課題 1 件あたりの費用は 0.22 / 0.33 / 0.38 ドルでした(フックありには、作業を外部の実装ツールに回した分の費用は含まれていません)。件数が少なく参考値ですが、
事前の取り決めや作業の振り分けは、この規模では費用と時間を増やしただけでした。
そのため、このプラグインは事前の手順を足さず、**終わる瞬間の検査だけ**を持ちます。
この実験で、エージェントが編集ツールを使わずにシェルのスクリプトでファイルを書き換え、
編集を見張るゲートを素通りしていたことも見つかりました。`shell_writes.py` はその対策です。

## 信頼の境界と、向いている場面

- ゲートは、エージェントのうっかりを止めるためのもので、悪意のあるエージェントを止めるものではありません。
  エージェントは `.claude/test_gate.json` を書き換えられますし、「未検証」と書けば done の判定を通れます。
  後者は意図した逃げ道で、確かめられないことを正直に書かせるためのものです。
- `test_gate` はリポジトリに置かれたコマンドをシェルで実行します。信頼できないリポジトリでは有効にしないでください。
- `test_gate` が見るのは「テストが通ったか」だけです。エージェントがテストの期待値のほうを書き換えても通ります
  (実際の動作確認で、仕様の変更に合わせてテストの期待値を書き換えて通した例がありました。このときは正しい対応でした)。
  テストの変更が正当かどうかは、差分を人が見る必要があります。
- ask の判定は、「自分で決められることを聞いて止まる」のを減らす向きに作っています。承認や権限が中心の業務エージェントでは、
  聞かない誤りのほうが高くつくため、この向きのまま使うべきではありません。分類(不可逆・外部送信など)を
  常に人に確かめる側に使う設計が合います。

## 公開前チェック(`tools/publish_check.py`)

個人のリポジトリから漏れるのは、パスワードよりも、設定に残ったホームディレクトリのパス、コメントに残った
私的な案件名、コミットに残った作者名です。このツールは、公開されるファイルとすべてのコミットを機械で調べます。

| 検査 | 内容 |
|---|---|
| denylist | リポジトリの外に置いた禁止語リスト(名前・案件名など)。リストがリポジトリの中にあると実行を拒否し、結果には語そのものを出さない |
| pii | メールアドレス、ホームディレクトリのパス、電話番号、郵便番号、私的なネットワークのホスト名 |
| secrets | 内蔵のパターンと gitleaks(ファイルと履歴) |
| identity | すべてのコミットの作者・コミッターと、次のコミットに使われる名前 |
| history | 過去のすべての版とコミットメッセージ(後で消しても履歴には残る) |
| unicode | ソースの見た目と中身を変える双方向制御文字 |
| files | `.env`・鍵・会話記録など公開すべきでない種類のファイル、大きすぎるファイル |

このリポジトリ自体を公開する前にも、このツールで次の 3 件が見つかり、直しています。

- 検査器の双方向制御文字の検出パターンに、制御文字そのものが入っていた(エスケープで書いたつもりが、文字として書き込まれていた)
- テストの例に、手元の環境でしか意味のない識別子が残っていた
- git の作者名が、公開用のアカウント名になっていなかった

## インストール

```bash
claude plugin marketplace add resoresot/evidence-gates
claude plugin install evidence-gates@evidence-gates
```

テストゲートを使うリポジトリには `.claude/test_gate.json` を置きます。

```json
{"command": "npm test", "max_iterations": 3, "timeout": 600}
```

変更ファイルで走らせるテストを分ける形もあります(`gates/test_gate.py` の先頭を参照)。

| 環境変数 | 意味 |
|---|---|
| `EVIDENCE_GATES_DISABLE` | `all`、または `completion,test,zsh_glob,lessons` のうち止めたいもの |
| `EVIDENCE_GATES_SKIP` | completion の中の `done,ask,lang` のうち止めたいもの |
| `EVIDENCE_GATES_JUDGE` | `rule`(既定)、または `sonnet` などのモデル名。done と ask を LLM に判定させる(`haiku` は評価で不要に止める割合が高かった) |
| `EVIDENCE_GATES_DONE_RULE` | `shadow`(既定:規則の done は記録だけ)、または `block` |
| `EVIDENCE_GATES_LOG_DIR` | 判定の記録の置き場(既定はプラグインのデータフォルダ) |
| `EVIDENCE_GATES_LESSONS` | 学びの保存先(既定は `~/.config/evidence-gates/lessons.jsonl`) |

## 開発

```bash
cd tests && python3 -m unittest                       # 単体テスト(フックとしての入出力と、計測の道具も含む)
python3 tools/publish_check.py . --require-denylist --require-gitleaks
python3 tools/replay.py --before YYYY-MM-DD           # ゲートを入れた日より前の記録で測る
python3 tools/stats.py --log <events.jsonl>           # 稼働中のゲートの週ごとの発火率
python3 eval/score.py --dir eval/synthetic --gold labels_intended.jsonl   # 規則と LLM の比較(合成データ)
claude plugin validate .
```

依存は Python 3.10 以上の標準ライブラリだけです(LLM モードでは Claude Code の CLI を使います)。

## 限界

- 規則の判定は、「完了」「確認します」などの言い回しを日本語と英語の一部しか見ていません。
- 実測の数字は作者 1 人の記録で、当てはまる場面が少ない(done 1 件、ask 5 件)ため、本物の記録での区間は広くなっています。
- ask の「聞く必要があったか」は使う人の好みに左右されます。作者の判定は、正解を付けた Opus より厳しめでした。
- `zsh_glob_gate` は zsh の既定の挙動を前提にしています(bash では一部の形だけを止めます)。
- 学びの関連度は語の重なりで判定しているため、言い換えには弱いです。
