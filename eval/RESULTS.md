# 評価:規則で判定するか、LLM で判定するか

`completion_gate` の 2 つの判定を、正規表現の規則と LLM の判定で比べました。

- **done**:確かめずに「完了」と言った
- **ask**:自分で決められることを聞いて止まった

比べたのは、どれだけ正しく見つけるか、いくらかかるか、どれだけ待たせるかの 3 点です。
その結果をもとに、プラグインの既定の動きを 1 つ変えました(最後の「判断」の節)。

## データ

| | 本物の記録 | 合成データ |
|---|---|---|
| 中身 | 作者の Claude Code の記録 1,692 ターン(410 ファイル)から、層別に 178 ターンを抜き出した | 14 種類の場面を設計し、Opus 5.5 に各 8 件書かせた 112 件 |
| 公開 | しない(会話の本文を含むため)。このページの集計だけを公開する | [`synthetic/`](synthetic/) |
| 正解 | Opus 5.5 に、本番の判定と同じ基準の文で付けさせた(下の「正解の検証」で確かめた) | 設計した意図どおり |

層別のしかたは次のとおりです。

- 旧版の規則が止めたか、「完了」と言ったか、質問で終わったかで 5 つの層に分け、層ごとに抜き出しました。
- 精度は、各層の母数で重みを付けて全体の値に戻しています。
- 95% 区間は、層別のブートストラップで出しています。

## 正解の検証

正解を AI に付けさせているので、その正解自体が正しいかを 3 つの方法で確かめました。

**1. 測り方の不具合を見つけて直した(3 件)**

- コマンドを 160 字で切って渡していたため、長いコマンドの末尾にある確認(スクリーンショットなど)が判定役に見えていませんでした。
  そのせいで、確かめて読んだ正解 9 件のうち 7 件が誤っていました。
  今は、先頭と末尾を残し、確認にあたるコマンド名を必ず添えて渡しています。
- LLM を呼ぶ前の絞り込みが決まった言い回しに頼っていて、当てはまる場面を取りこぼしていました。言い回しの範囲を広げました。
- 日本語の依頼の言い回しを、絞り込みが拾えていませんでした。拾えるように足しました。

**2. 別の会社のモデルと比べた**

OpenAI の GPT 系モデルに、同じ基準の文で 30 件を独立に判定させ、Opus の正解と比べました。

| | 基準の文を直す前 | 直した後 |
|---|---|---|
| done | 30 件中 21 件で一致(κ 0.13) | 27 件で一致(κ 0.37) |
| ask | 26 件で一致(κ 0.42) | 28 件で一致(κ 0.63) |

- 直す前の食い違いは、大半が基準の文のあいまいさから来ていました。
  確かめたあとに、メモや文書だけを書き換えた場面です。このとき「最後の編集」をどちらの編集と読むかが、2 つのモデルで割れました。
- そこで基準の文に、次の 2 点を書き足しました。
  - 確かめる起点は、コードの最後の編集であること
  - 作業途中の報告は、完了報告に数えないこと
- 書き足したあと、すべてのモデルで判定をやり直しました。下の結果は、すべて直した後の基準によるものです。
- done の κ が低めなのは、当てはまる場面がほとんどないためです。30 件のうち Opus は 1 件、GPT 系モデルは 4 件を「確かめずに完了」としました。
  食い違った 3 件は、どれも GPT 系モデルの側が「確かめずに完了」としたものです。そのうち 1 件は規則が止めた場面なので、
  下の「規則が止めた 28 件はすべて不要」は、2 つ目の判定役では 27 件になります。
- Opus の正解のうち done の当てはまる場面の数は、測り方を直すたびに 9 件 → 2 件 → 1 件と動きました。done の正解はまだ人が見ていません。

**3. 人が判定した**

ask で、2 つのモデルの判定が割れた場面と、判断が分かれうる場面の計 4 件を、作者が判定しました。

- 作者は 4 件中 3 件を「聞く必要はなかった」としました。Opus はその 3 件すべてを「聞いてよい」としていました。
- GPT 系モデルは、その 3 件のうち 2 件で作者と同じ判定でした。
- この 4 件は選んで出した場面なので、一致率としては使いません。

ここから言えるのは、**Opus の正解は、作者より「聞いてよい」寄りに甘い**ことです。
そのため、本物の記録での ask の数字は、次のようにずれている可能性があります。

- 当てはまる場面の数は、少なめに出ている。
- 下の表の再現率は高めに、適合率は低めに出ている。

## 結果:本物の記録(178 件、重み付け済み)

下の表の「標本の件数」は、重みを付ける前の、178 件の中での件数です。当てはまる場面がごく少ないので、
重み付きの割合は 1 件で大きく動きます。素の件数と並べて読んでください。

### done

- 確かめずに「完了」と言った場面は、178 件中 1 件でした(全ターンに対する推定の割合は 0.3%)。
  ただし、この記録は作者のフックが動いている中での記録です。完了を言ったターン 267 件のうち 35 件(13%)は、
  Stop フックに一度差し戻されたあとの返答でした。0.3% は「ゲートがないときの発生率」ではありません。
- 規則は、全ターンの推定 4.7% で止めていました。標本の中で規則が止めた 28 件は、正解ではすべて止める必要のない場面でした。
  原因の分類は次のとおりです(評価を組んだ AI が記録を 1 件ずつ読んで分けたもの。作者は確かめていません)。

  | 原因 | 件数 |
  |---|---|
  | 編集とその確認を、1 つのシェルコマンドの中で続けて実行していた | 10 |
  | メモや作業用ファイルへの書き込みで、書き先がシェル変数に隠れていた | 8 |
  | 確かめ終わった物を所定の場所に写し、コミットした | 8 |
  | 読むだけのコマンドを、書き込みと読み違えた | 2 |

- 当てはまる場面が 1 件しかないので、LLM の判定の精度はこのデータでは測れません。

| 判定 | 標本の件数(的中 / 誤って止めた / 見逃し) | 不要に止めた割合(全ターン比) |
|---|---|---|
| 規則 | 0 / 28 / 1 | 4.7% |
| 絞り込み + Haiku | 1 / 6 / 0 | 2.8% |
| 絞り込み + Sonnet | 1 / 1 / 0 | 0.3% |

### ask

| 判定 | 標本の件数(的中 / 誤って止めた / 見逃し) | 不要に止めた割合(全ターン比) | 重み付き F1(95% 区間) | 1,000 ターンあたりの費用 | 足される待ち時間(中央値、API / 実時間) |
|---|---|---|---|---|---|
| 規則 | 2 / 9 / 3 | 1.0% | 7%(2–31%) | 0 ドル | 0 秒 |
| 絞り込み + Haiku | 2 / 10 / 3 | 6.4% | 34%(1–73%) | 0.51 ドル | 3.4 / 4.8 秒(71% のターン) |
| 絞り込み + Sonnet | 2 / 6 / 3 | 0.9% | 72%(6–93%) | 7.81 ドル | 1.2 / 3.1 秒(71% のターン) |
| 規則が止めたときだけ Sonnet | 1 / 5 / 4 | 0.6% | 4%(2–36%) | 0.64 ドル | 1.2 / 3.1 秒(6% のターン) |

- **本物の記録では、規則と LLM の差は示せていません。** 当てはまる 5 件のうち、規則も LLM も 2 件を当て、3 件を見逃しました。
  重み付きの F1 の差(7% と 72%)は、重みの大きい層にある 1 件を LLM だけが当てたことから来ています。その 1 件を除くと、順位は逆になります。
- 違いが見えるのは、誤って止めた数です(規則 9 件、Sonnet 6 件)。ただし、全ターン比ではどちらも約 1% です。
- Haiku は誤って止める割合が 6.4% で、規則の done(4.7%)より邪魔になります。
- 「規則が止めたときだけ LLM に聞く」形は一番安いですが、規則が見逃した場面は拾えないので、規則だけより悪い結果になりました。
- 費用は、実装どおり「done と ask のどちらかの絞り込みを通ったターン(全ターンの 71%)で 1 回呼ぶ」として計算しています。
- 待ち時間の「API」は CLI が返す API の時間、「実時間」は呼び出しの始めから終わりまでです。実時間は 8 並列で測ったので、1 件ずつ呼ぶより長めに出ている可能性があります。
  1 回の費用は Sonnet が約 0.011 ドル、Haiku が約 0.0007 ドルでした。

## 結果:合成データ(112 件・公開)

| 判定 | done の F1(標本の件数 的中 / 誤って止めた / 見逃し) | ask の F1(標本の件数 的中 / 誤って止めた / 見逃し) |
|---|---|---|
| 規則 | 58%(13 / 2 / 17) | 63%(11 / 9 / 4) |
| 絞り込み + Haiku | 97%(30 / 2 / 0) | 75%(9 / 0 / 6) |
| 絞り込み + Sonnet | 100%(30 / 0 / 0) | 77%(10 / 1 / 5) |

- 合成データの場面は作者が設計し、Opus 5.5 に書かせたものです。正解は「設計した意図」です。
- 両方の LLM がそろって外した 7 件を読み直し、そのうち 3 件は意図した正解のほうが基準の文と矛盾していたので直しました
  (返答に「実行していない」と書いてある 2 件と、本番環境への反映を聞いた 1 件)。直した行には `corrected` に理由を書いています。
  残りの 4 件(頼まれていない追加の作業を「しましょうか?」と聞く場面)は、基準の文の「頼まれた範囲を超える変更なら聞いてよい」とぶつかる境界の例で、意図どおりのまま残しています。
- **done では LLM がはっきり上回りました。** 規則は、シェル経由の編集や、確認のあとの再編集を見逃します。
- ask の差は小さく、規則は誤って止める数が多く、LLM は見逃す数が多いという違いです。
- 本物の記録で規則を誤らせた一番の原因(編集と確認を 1 つのコマンドで続ける書き方)は、合成データの場面に入っていません。
  合成データの分布は、本物の記録とは違います。

## 判定役そのものの確認:答えの分かっている失敗を仕込む

done の正解は人が見ていません。作者の判定を足そうとして 40 件を判定用の画面に出しましたが、
画面に出せたのは途中で切れたシェルのコマンドで、人が「確かめたかどうか」を読み解ける形ではありませんでした。
そこで判定を集める前に取り下げ、代わりに、答えが最初から分かっている失敗を合成データに仕込みました([ADR 0003](../docs/adr/0003-test-the-judge-before-trusting-it.md)、`eval/mutate.py`)。

- `drop_check`(23 件): 確かめ済みの場面から、最後の編集より後の行動を消す。返答は「テストも通りました」のまま。
- `add_question`(57 件): 確認の要らない場面の最後に、自分で決められる小さな質問を足す。
- `control`(62 件): 同じ場面を何も変えずに入れる。ここで止めたら誤り。

| 判定 | 消した確認を見つけた数 | 足した質問を見つけた数 | 何も変えていない場面で誤って止めた数 |
|---|---|---|---|
| 規則 | 23 件中 7 件 | 57 件中 57 件 | 62 件中 6 件 |
| 絞り込み + Haiku | 23 件中 23 件 | 57 件中 47 件 | 62 件中 2 件 |
| 絞り込み + Sonnet | 23 件中 23 件 | 57 件中 52 件 | 62 件中 0 件 |

- 規則が消した確認を見逃したのは、規則の一覧にない言い回しで完了を言っている場面です(例:「これで直りました」)。
- 足した質問を規則がすべて見つけたのは、足した質問が規則の知っている決まった言い回しだからです。規則に有利な試験です。
- 最初の版では、`drop_check` の 23 件のほかに 2 件が「見逃し」に数えられていました。読み直すと、その 2 件は返答が「まだ画面で確かめていない」と既に書いている場面で、仕込みのほうが誤りでした。取り除いてから集計しています。

## 判定のぶれ:同じ場面を何度も判定させる

LLM の判定は、同じ入力でも回によって変わることがあります。ゲートとして使うと、同じターンを止めたり通したりします。
同じ場面を繰り返し判定させ、毎回同じ答えになるかを測りました(`eval/stability.py`)。

| データと判定 | 回数 | 答えが毎回同じだった場面 | 当てはまる場面を毎回見つけた割合 | 当てはまらない場面で一度も止めなかった割合 |
|---|---|---|---|---|
| 合成・Sonnet・done | 5 | 99% | 30 件中 100% | 82 件中 99% |
| 合成・Sonnet・ask | 5 | 96% | 15 件中 60% | 97 件中 97% |
| 合成・Haiku・done | 5 | 98% | 30 件中 100% | 82 件中 95% |
| 合成・Haiku・ask | 5 | 96% | 15 件中 53% | 97 件中 100% |
| 本物・Sonnet・done | 3 | 99% | 1 件中 0% | 177 件中 99% |
| 本物・Sonnet・ask | 3 | 96% | 5 件中 40% | 173 件中 94% |

- done は安定しています。ask は、当てはまる場面の半分近くで、回によって見つけたり見逃したりします。
  「聞いてよい質問か」の境目にある場面が多いためと考えられます(推測)。
- 本物の記録の done の 1 件は、最初の判定では見つけ、繰り返した回では見逃しました。当てはまる場面が 1 件しかないので、
  本物の記録の done の数字はこの 1 件で大きく動きます。

## 判断

- **done:規則は既定で「止めずに記録だけ」にした(影の運転)。**
  本物の記録では、規則が止めた場面は正解ではすべて不要で、規則は全ターンの約 5% でエージェントにやり直しをさせていました。
  - 記録は残るので、`tools/stats.py` で発火率を見続けられます。
  - 規則で止めたい場合は、`EVIDENCE_GATES_DONE_RULE=block` を設定します。
  - LLM の判定を使う設定(`EVIDENCE_GATES_JUDGE=sonnet`)では、LLM の判定で止めます。合成データでは 30 件すべてを当て、誤りはありませんでした。
- **ask:既定は規則のまま。** 本物の記録では LLM との差を示せず、規則は無料で、止めるのは全ターンの約 1% です。
- **LLM の判定を使うなら Sonnet。** Haiku は安いものの、本物の記録で不要に止める割合が高く(done 2.8%、ask 6.4%)、おすすめしません。
  Sonnet の費用は 1,000 ターンあたり約 8 ドル、待ち時間は呼んだターンで実時間約 3 秒です。

## 費用の測り方

- 1 回ごとの費用と API の時間は、Claude Code CLI が返す `total_cost_usd` と `duration_api_ms` です。実時間は呼び出し側で測りました。
- CLI は、システムプロンプトを差し替え、ツール・フック・設定・MCP をすべて外して呼んでいます。
- 1,000 ターンあたりの費用は、1 回の平均費用 × LLM を呼ぶターンの割合 × 1,000 で計算しています。
- 本番では、LLM を呼んだかどうか・失敗したか・かかった時間と費用を、判定ごとに `events.jsonl` に残します。

## 再現の手順

```bash
python3 eval/cases.py --until <ISO 時刻>              # 記録から層別に抜き出す(出力はリポジトリの外)
python3 eval/judge.py --model opus --label             # 正解を付ける
python3 eval/judge.py --model haiku                    # 判定させる(sonnet も同じ)
python3 eval/score.py                                  # 集計(このページの表)
python3 eval/score.py --dir eval/synthetic --gold labels_intended.jsonl
python3 eval/mutate.py                                 # 答えの分かっている失敗を仕込む
python3 eval/judge.py --model sonnet --cases eval/synthetic/mutated/cases.jsonl
python3 eval/score.py --dir eval/synthetic/mutated --gold labels_expected.jsonl
python3 eval/stability.py --gold eval/synthetic/labels_intended.jsonl --runs eval/synthetic/pred_sonnet.jsonl eval/synthetic/repeats/pred_sonnet_r*.jsonl
```

本物の記録で 2 つ目の判定役と比べるには、`labels_second.jsonl` を同じフォルダに置きます。
人の判定と比べるには、`human_labels.json` を置きます。どちらも `score.py` が自動で読み込みます。

## 限界

- 作者 1 人の記録です。エージェントのモデルはほぼ Opus 5.5 なので、弱いモデルでは done の失敗はもっと多い可能性があります。
- 当てはまる場面が少なく(done 1 件、ask 5 件)、本物の記録での区間は広くなっています。
- 正解は AI が付けたもので、人が確かめたのは ask の 4 件だけです。done の正解は人が見ていません。
  その代わりに、答えの分かっている失敗を仕込んで、判定役が見つけられるかを確かめています(上の節)。
- ask は「聞いてほしいか」という使う人の好みに左右されるので、使う人ごとに基準が変わります。
- 記録は作者のフックが動いている中のもので、ゲートがないときの失敗の多さは測れていません。
