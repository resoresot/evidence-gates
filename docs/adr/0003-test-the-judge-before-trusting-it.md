# ADR 0003: 判定の正しさは、ラベルとの一致だけでなく、答えの分かっている失敗を仕込んで確かめる

- 状態: 採用(2026-11-19)
- 関係するファイル: `eval/mutate.py`、`eval/stability.py`、`eval/score.py`、[eval/RESULTS.md](../../eval/RESULTS.md)

## 状況

本物の記録での評価には、次の弱点がある。

- 正解は AI(Opus 5.5)が付けた。別の会社のモデルとの一致は確かめたが、done の正解は人が見ていない。
- 当てはまる場面が少ない(done 1 件、ask 5 件)。
- 作者の判定を足そうとして、done の 40 件を判定用の画面に出した。しかし画面に出せたのは途中で切れたシェルのコマンドで、
  「確かめたかどうか」を人が読み解ける形ではなかった。判定を集める前に取り下げた。

## 決定

done は「記録を見れば決まる事実」なので、人の読み解きに頼らず、答えの分かっている失敗を仕込んで確かめる。

- `drop_check`: 確かめ済みの場面から、最後の編集より後の行動を消す。返答は「完了」のままなので、確かめずに完了になる。
- `add_question`: 確認の要らない場面の最後に、自分で決められる小さな質問を足す。
- `control`: 同じ場面を何も変えずに入れる。ここで止めたら誤り。
- LLM の判定は同じ場面を複数回流し、毎回同じ答えになるか(`stability.py`)も確かめる。

ask は「利用者が聞いてほしいか」で決まるので、利用者(作者)の判定を正解の確認に使う。

## 検討した案

| 案 | 退けた理由 |
|---|---|
| 人が done の正解を付ける | 判定に要る情報(コマンドの中身と順番)を、人が読める形で見せられなかった。読める形に AI が言い換えると、AI の読み方が正解に入る |
| AI の正解だけで済ませる | 判定役がそもそも失敗を見つけられるかは、AI 同士の一致では分からない |

## 結果

- 仕込んだ失敗で、規則は「確かめずに完了」を 23 件中 7 件しか見つけられなかった(規則にない言い回しの完了報告を読めない)。LLM は 23 件すべてを見つけた。
- 足した質問は、規則がすべて見つけた。ただし足した質問は規則が知っている決まった言い回しなので、規則に有利な試験である。
